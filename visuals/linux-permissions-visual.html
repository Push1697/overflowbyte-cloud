Linux Permissions, Visually

An interactive deep dive into kernel process credentials, newgrp, in-memory inodes, and Discretionary Access Control (DAC).

1

The Stale Groups Dilemma (Why usermod -aG Fails Open Shells)

When a sysadmin adds you to a group, your open terminal does not inherit it. Here is the lifecycle timeline:

1
Interactive Shell Spawned (PID 1042)

PAM reads /etc/passwd and /etc/group at login. The kernel creates struct cred cached in RAM.

2
Sysadmin runs usermod -aG developers alice

The text file /etc/group on disk is updated. But running processes are completely decoupled from disk text files!

3
Alice runs cd /opt/projects/dev → Permission Denied

The kernel evaluates PID 1042's existing in-memory struct cred. The group list still contains only her old groups.

4
The Fix: newgrp developers

Runs a setuid-root binary that verifies /etc/group, calls setgroups() and setgid(), and spawns a refreshed subshell!

💡 Key Insight: Linux processes never poll /etc/group. Credentials are an immutable, reference-counted in-kernel object.
2

Kernel Structure: task_struct → struct cred

Every thread has a task_struct pointing to its struct cred. Notice the 4 distinct IDs maintained by the kernel:

Credential Field Name Actual Kernel Role
uid / gid Real ID Identifies the actual user who spawned the process. Determines signal delivery permissions (who can kill this process).
euid / egid Effective ID Used for general authorization, creating IPC primitives, and evaluating privileged capabilities.
suid / sgid Saved Set-ID Preserves the prior effective ID when executing setuid binaries, allowing processes to drop and re-elevate privilege safely.
fsuid / fsgid Filesystem ID The actual ID used for file access! When the kernel checks inode permissions in VFS, it compares against fsuid, not euid!
⚠️ Technical Fix: NFS servers and userspace file servers historically inspired fsuid so they could impersonate user file access without exposing process signals or non-filesystem capabilities.

Inodes & Dentry Path Resolution Flow

When a process opens /var/log/app.log, Linux navigates the filesystem cache before touching disk blocks:

1. Dentry Cache (RAM)

Kernel checks hash table of directory entries. Resolves filename string to Inode number in sub-microsecond RAM lookup.

↓ Cache Miss?
2. Inode Table (Disk → VFS Inode in RAM)

Reads block group descriptor and inode bitmap from disk. Loads struct inode (128/256 bytes) containing i_mode, i_uid, i_gid, size, and extent tree.

↓ Access Granted?
3. Page Cache & Data Blocks

Reads extent pointers from inode and streams 4KB physical disk blocks into system page cache.

SGID Directory Interactive Demo

Observe file creation behavior when the SetGID bit (2xxx) is applied to a directory:

📁 Standard Directory (0775)

Directory owned by alice:developers

$ touch /data/plain/report.txt $ ls -l /data/plain/report.txt -rw-r--r-- 1 bob bob 0 Oct 25 10:00 report.txt

❌ File group defaults to Bob's primary group (bob). Team members in developers cannot write to it!

🚀 SGID Directory (2775 / drwxrwsr-x)

Directory owned by alice:developers with SGID

$ touch /data/collab/report.txt $ ls -l /data/collab/report.txt -rw-r--r-- 1 bob developers 0 Oct 25 10:00 report.txt

✅ The kernel inherits the parent directory's GID (developers). New subdirectories automatically inherit the SGID bit too!

Try It Yourself: Live Verification Script

Run these commands in any Linux terminal to verify your shell's live kernel credentials and Inode metadata:

# 1. Inspect all 4 UIDs and GIDs of your current shell process
grep -E 'Uid|Gid|Groups' /proc/$$/status

# 2. Inspect Inode metadata, permissions, and raw octal
stat -c "File: %n | Inode: %i | Octal Mode: %a | Access: %A | Owner: %U(%u):%G(%g)" /etc/passwd

# 3. Simulate newgrp and observe subshell GIDs
newgrp developers
grep -E 'Gid|Groups' /proc/$$/status
exit
