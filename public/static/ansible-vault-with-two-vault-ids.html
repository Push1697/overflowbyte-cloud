01 — SECRETS ARCHITECTURE

Unattended multi-environment secret management

In production CI/CD pipelines, typing interactive vault passwords is impossible. Ansible Vault with multiple vault IDs (--vault-id dev@~/.vault_dev --vault-id prod@~/.vault_prod) allows encrypting staging and production credentials under different keys within the exact same Git repository.

MULTI-ENVIRONMENT
Vault ID Labeling
Ciphertext headers store $ANSIBLE_VAULT;1.2;AES256;dev. Ansible matches the correct password file automatically.
VAULT IDs
GRANULAR SECRETS
encrypt_string
Encrypt single sensitive variables inline inside otherwise plaintext YAML files instead of locking the entire file.
INLINE CIPHER
RUNTIME DEFENSE
no_log: true
Vault protects secrets at rest on disk. no_log: true protects secrets in memory and console logs during execution.
LOG REDACTION
MODULARITY
Decomposition into Roles
Eliminate monolithic 500-line playbooks by scaffolding clean, isolated roles (common, apache, users, security).

02 — FULL FILE VS INLINE ENCRYPTION

Architectural trade-offs of secret storage

Attribute Full-File Encryption Inline (encrypt_string)
Git Diff Visibility Opaque ciphertext block; diffs are unreadable Plaintext structure preserved; only secret is masked
Merge Conflict Risk High (cannot resolve line-by-line) Low (standard git merge applies)
Performance Overhead Decrypted once per file load Evaluated per variable string
Multi-Key Mixing Single vault ID per file Can mix multiple vault IDs in one YAML
